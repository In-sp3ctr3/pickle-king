# Pickle King engineering profile

Verified 2026-10-02 for [SPE-189](https://linear.app/spectreos/issue/SPE-189/audit-pickle-king-and-adopt-the-current-project-harness); the harness baseline was updated 2026-10-03 for [SPE-215](https://linear.app/spectreos/issue/SPE-215/update-pickle-king-harness-to-the-spe-214-steward-baseline). Product facts remain in [README](../../README.md), [AGENTS](../../AGENTS.md), [specs router](../../specs/README.md), and [ADRs](../architecture). This profile records the harness interface and observed gaps.

## Product and boundaries

Pickle King is an offline-first, one-route tournament and scoring PWA. Organizer input flows through React and deterministic `src/tournament/` and `src/match/` rules to validated browser storage. PNG export is user-initiated. There are no accounts, server API, database, queue, AI product behavior, or product analytics on the current `main`; see [ADR-0001](../architecture/adr-0001-local-first-single-app.md) and the [threat model](../security/threat-model.md). The architecture planning branch at `605c937` is product-control-plane material, not adopted mainline behavior.

Node is `>=22.13.0`; CI uses 22.13. Python 3.9+ is needed for harness checks and read-only hygiene. npm and `package-lock.json` own dependencies. Vinext/React builds a service-worker PWA for Sites; [ADR-0002](../architecture/adr-0002-vinext-sites.md) requires `vinext check` and a production build. No test credentials or external services are needed for current checks. Local start: `npm ci && npm run dev`. Supported CI platform: Ubuntu 24.04; macOS local checks may differ in canvas antialiasing.

CI Quality runs `./scripts/verify --full` on PRs and `main`; CodeQL and Dependency Review remain separate workflows. A passing check covers its recorded commit and mode only. Match the exact current PR head before merge and the exact merged commit afterward. Record skipped checks. [Lifecycle](LIFECYCLE.md) owns continuation and review; [release evidence](RELEASE.md) owns readiness; the [provenance manifest](HARNESS_PROVENANCE.json) owns the adopted OS revision.

Normal ticket prompts are generated with `scripts/eng-ticket-prompt TICKET pickle-king`. Feedback is appended through `scripts/eng-os-feedback` to an explicitly supplied existing private Engineering OS ledger using the exact OS runtime pinned by the provenance manifest and a verified Steward registry that authorizes the ticket, run, and reporter. Pickle King owns neither the ledger schema nor Steward policy, and the adapter fails closed instead of creating a repository-local fallback.

`scripts/harness-status --gate` is a direct lifecycle gate in addition to Steward stocktake. It exits nonzero unless the action is `no_action_required`; the accepted SPE-214 stocktake does not independently surface local drift when the adopted SHA already equals the accepted SHA.

## Environments and release limits

Local `npm run dev` and built `npm run start` are observed. The repository describes Sites deployment and `NEXT_PUBLIC_SITE_URL`, but does not contain a verified preview/staging/production identity or native deploy/rollback command. `scripts/verify` does not certify a deployed environment. No `scripts/smoke` or `scripts/release-check` is installed until a real target identity and safe probe can be verified. The current product has no migration or feature-flag provider. A release must record candidate/source/artifact, target identity and configuration, current review/CI, actual smoke/QA, rollout owner, stop conditions, and rollback or forward-recovery route before readiness is claimed; see [RELEASE](RELEASE.md).

Highest risks: stale offline service workers during play, invalid persisted snapshots, score/tournament invariants, accidental share disclosure, canvas rendering differences, and dependency changes in the Vinext/Cloudflare build. Preserve the current regression fixtures and [share-image gate](../../AGENTS.md) for share changes.
