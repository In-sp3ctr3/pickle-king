# Ticket and PR lifecycle

Adapted from Project Harness at `e566213e527802f6ab305486bde26a10dfb07975`. [SPE-189](SPE-189.md) records the initial adoption and [SPE-215](SPE-215.md) records the Steward feedback update. Linear owns scope/status, Git owns source, and GitHub owns PR/check/review state.

1. At start or resume, read the Linear issue and latest comments, then fetch remotes, inspect branch/worktree/status/stashes/PRs, and run `scripts/repo-hygiene` read-only against the verified canonical branch. Resolve unknown overlapping work before a new branch. Use the relevant `specs/` workspace for product work; SPE-189 is repository harness work.
2. Use `.work/active/<ticket>/STATE.md` only as an ignored cache. Reconcile its claims with Linear, Git, PR and current files. If absent, reconstruct from those authorities; a cache timestamp is not evidence. The [STATE template](STATE.md) lists useful handoff fields.
   Reconstruct Engineering OS feedback from the OS-owned run ledger before trusting the cache. Distinguish unassessed feedback, explicit `os_feedback: none`, and unresolved observation IDs; a later clean assessment does not close an earlier observation.
3. Keep a bounded plan and acceptance-to-check map beside the owning ticket or feature workspace. For consequential work, obtain fresh independent plan and implementation reviews using the shared [Engineering Design Contract](https://github.com/In-sp3ctr3/codex-os/blob/e566213e527802f6ab305486bde26a10dfb07975/docs/engineering/ENGINEERING_DESIGN_CONTRACT.md) and code-review owner. Record findings, fixes and rechecks; an implementer does not approve their own subjective work.
4. Before PR, review the actual diff, run applicable verification, and record unrun checks. The PR template records acceptance, revision, reviewer and risk. Hosted checks and conversations must cover the exact current PR head; old-head green checks do not establish readiness. A merge changes the candidate and needs verification on the merged commit.
5. Before Done, rerun read-only hygiene. Classify every dirty path, branch, worktree, stash and open PR with owner, disposition and evidence. Preserve unknown or user-owned data. Release, deployment, observation and cleanup are separate evidence gates described in [RELEASE](RELEASE.md); a merge alone does not prove them.

Generate normal execution prompts with `scripts/eng-ticket-prompt TICKET pickle-king`; the mandatory [Engineering OS feedback footer](OS_FEEDBACK_FOOTER.md) is part of every generated prompt. Before a meaningful checkpoint or Done, assess feedback and pass one controlled JSON assessment to `scripts/eng-os-feedback --os-repo <exact-adopted-codex-os-checkout> --ledger <existing-private-ledger> --registry <verified-steward-registry>`. The adapter authenticates the repository, ticket, run, and reporter against the registry, verifies the exact OS runtime pinned by the provenance manifest, and never creates a fallback ledger. Missing or malformed feedback, unavailable ledger/registry, or an unregistered reference remains a visible gap rather than implicit `none`.

Run `scripts/harness-status --gate` directly at start/resume and before checkpoint or Done. Its `action` must be `no_action_required`; a relevant shared delta or local drift exits nonzero and blocks the gate even when the adopted and accepted OS SHAs match. Steward stocktake is supplementary evidence, not a replacement for this direct gate: the accepted SPE-214 consumer does not emit same-SHA local drift. Preserve that limitation as Engineering OS feedback until the shared consumer is repaired; do not falsify an adopted SHA to force visibility.

Record only the ledger reference, assessment ID, observation IDs, concise classification/disposition, and unresolved immediate signals in the ignored checkpoint. Never store raw evidence, paths, secrets, or transcripts there. Product sessions supply evidence to Steward stocktake; they do not create or mutate global OS policy.

The read-only hygiene command accepts `--canonical origin/main --github-repo In-sp3ctr3/pickle-king --fetched`; add `--phase start --ticket ID --scope PATH` for a bounded start gate. Fetch first. Its report is evidence, not permission to delete. Branches and worktrees with unique product architecture or dependency work remain under their owners.
